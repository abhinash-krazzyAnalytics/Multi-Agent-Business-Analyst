# Multi-Agent Business Analyst

A local, Ollama-powered multi-agent analytical assistant with a Claude-styled
chat UI (Gradio), built around a Master → {Text-to-SQL → Analyst} / Thinker →
Visualization workflow.

## What's here

- **Master Agent** — routes each question to the database path, the general
  reasoning path, or asks for clarification. Reads recent analytical history
  to interpret follow-ups ("compare it with 2024", "break it down by region").
- **Text-to-SQL Agent** — turns a question into read-only SQLite SQL.
- **SQL Validator** — a hard Python gate: only `SELECT`/`WITH`, no writes, no
  chained statements, only known tables/columns, row-limit enforced.
- **Analyst Agent** — turns query results into a plain-language summary, key
  metrics, insights, and (when useful) a chart recommendation. Never invents
  numbers — growth rates etc. are computed deterministically, not guessed.
- **Thinker Agent** — answers general questions that don't need the database.
- **Chart tool** — renders the Analyst's chart recommendation as a Plotly
  figure. The LLM never writes chart code, only picks type + columns.
- **Memory** — every turn's question/route/SQL/filters/summary is persisted
  to `memory/conversation_store.db` (separate from the business database),
  so follow-ups can reuse prior filters.
- **Sample database** — `database/business.db`, ~2 years of synthetic daily
  sales across 4 regions, 4 categories, 16 products (with a visible seasonal
  + year-over-year growth pattern, generated by
  `database/create_sample_db.py`).

## Quick start

```bash
pip install -r requirements.txt
python app.py
```

Open the printed local URL. The app works immediately with **no LLM
required** — it falls back to deterministic, keyword/pandas-based versions
of each agent so you can see the full workflow (routing → SQL → validation →
execution → analysis → chart) end to end.

## Connecting a real local model (Ollama)

```bash
# install Ollama, then:
ollama pull qwen2.5:7b
ollama pull gemma3:4b
ollama serve
```

Restart `python app.py`. The header will switch from "Demo mode" to
"Connected to local Ollama model", and each agent will call its assigned
model (see `config/settings.py` — `MODEL_CONFIG`, overridable via
`MASTER_MODEL` / `SQL_MODEL` / `ANALYST_MODEL` / `THINKER_MODEL` env vars)
instead of the offline fallback. If a call to Ollama fails for any reason
mid-conversation, that single agent quietly drops back to its fallback for
that turn rather than crashing the app.

## Try asking

- "What were monthly sales in 2025?" (data + chart)
- "Top 5 products in 2024" (data + chart)
- "Compare sales by region" (data + chart)
- "What about 2024?" as a follow-up (reuses prior filters)
- "What are the advantages of a star schema?" (general reasoning, no DB)

## Project structure

```
app.py                      Gradio chat UI (Claude-styled theme)
config/settings.py          Model assignment, paths, limits
graph/state.py              Shared AnalystState (TypedDict)
graph/workflow.py           Orchestration: routing, SQL/analyst loop, charts
agents/                     One module per agent (LLM call + offline fallback)
prompts/                    System prompts, extracted as constants
tools/
  llm_client.py             Ollama HTTP client + availability check
  schema_tool.py            Schema introspection (tables/columns/sample/date range)
  sql_validator.py          Read-only SQL safety gate
  sqlite_tool.py            Query execution
  chart_tool.py             Plotly chart rendering from structured config
  memory_tool.py            Persistent conversation/analytical history
database/create_sample_db.py  Regenerates database/business.db
```

## Design notes / things to know

- **Why not a literal `langgraph.StateGraph` here?** `graph/workflow.py` is
  written as a plain Python generator with *exactly* the same node shape
  LangGraph expects — every agent function takes and returns the shared
  `AnalystState` dict. That makes it a very small step to wrap each function
  as a LangGraph node (`workflow.add_node("master", run_master_agent)`, etc.)
  once you want LangGraph's checkpointing/persistence instead of the
  hand-rolled `memory_tool.py`. `langgraph`/`langchain` are already in
  `requirements.txt` for that migration.
- **Deterministic calculations.** Growth rates, totals, and top-N rankings
  are computed in Python (`agents/analyst_agent.py`'s fallback, or via the
  numbers the LLM is given), not left to the model to compute freely.
- **The offline fallback agents are intentionally simple** (keyword
  triggers + pandas), matching a handful of question shapes on this sample
  schema. They exist so the whole pipeline is runnable and testable without
  a GPU or a running Ollama server — swap in real models for real coverage.
- **Extending the schema:** if you point this at your own SQLite database,
  update `config/settings.py: DB_PATH`, and expect to revisit the
  Text-to-SQL fallback templates and prompts, since both currently assume a
  `sales(sale_date, region, category, product, amount, quantity)` shape.
